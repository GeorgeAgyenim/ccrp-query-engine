# Host setup guide

How a Colouring Cities (CCRP) instance, the *host*, runs the query engine next to its own platform. It is
written for the host's operator: someone who can run commands on the server and has the database owner's
login. Terms are defined in [CONTEXT.md](../CONTEXT.md).

Status: pre-release. This guide covers what exists today: the service, its database role, the field
catalogue, the `check` command and the query API. Sections marked *later* are filled in as the features
arrive.

## What the host supplies

| Item | Needed now | Notes |
|---|---|---|
| A PostgreSQL database with PostGIS and colouring-core's `buildings` and `geometries` tables | yes | Tested on PostgreSQL 18 with PostGIS 3.6. Footprints in EPSG:3857, as colouring-core stores them |
| A login for the engine, granted the role `query_engine_reader` | yes | [Create the engine's login](#create-the-engines-login) |
| The database owner's login, for the engine's migrations only | yes | Never given to the running service |
| A field catalogue file | yes | Generated by the engine's `catalogue` command: [The field catalogue](#the-field-catalogue) |
| Missing-value metadata | *later* | Which values count as missing, with evidence |
| A footprint provenance record | *later* | Source, licence, attribution |
| A language-model endpoint URL | *later* | OpenAI-compatible |
| A reverse-proxy route `/api/query/*` to the engine | when the host's UI calls it | [Reverse proxy](#reverse-proxy) |

## Prerequisites

To run from source: Node.js 26.13.1 (the version in `.nvmrc`) and npm 11, which ships with it. To run the
container: Docker with Compose. Either way, network access from the engine to the database.

## Settings

The service reads its settings from environment variables. Keep their values out of every repository; the
engine never logs or prints the database URLs, which hold credentials. Put them in the service's
environment, or in a file you keep out of version control and
load with Node's own `--env-file` (for example `node --env-file=/etc/query-engine.env src/main.ts`) or
Compose's `.env`.

| Name | Required | Default | Meaning |
|---|---|---|---|
| `QUERY_ENGINE_DATABASE_URL` | yes | none | `postgres://` URL for the engine's own login. To query a database copy (a frozen snapshot, say), point this at the copy |
| `QUERY_ENGINE_CATALOGUE_FILE` | yes | none | Path of the field catalogue file ([The field catalogue](#the-field-catalogue)). Also read by `check` |
| `QUERY_ENGINE_STATEMENT_TIMEOUT_MS` | no | `10000` | Longest any one statement may run, in milliseconds (1 to 2147483647). See [Statement timeout](#statement-timeout) |
| `QUERY_ENGINE_HOST` | no | `127.0.0.1` (`0.0.0.0` in the container) | Interface the HTTP server listens on |
| `QUERY_ENGINE_PORT` | no | `3100` | Port the HTTP server listens on |
| `QUERY_ENGINE_MIGRATION_DATABASE_URL` | for `migrate` only | none | `postgres://` URL for the database owner's login. Read only by the migrate command; never set it for the service |

Special characters in a password must be percent-encoded in a URL (`@` becomes `%40`, for example).

## Install from source

```sh
git clone https://github.com/GeorgeAgyenim/ccrp-query-engine.git
cd ccrp-query-engine
npm ci --omit=dev
```

## Run the engine's migrations

The migrations create the schema `query_engine` and the no-login group role `query_engine_reader`, and
grant that role `SELECT` on `public.buildings`, `public.geometries` and the engine's own tables, and nothing
else ([ADR-0007](decisions/0007-engine-schema-role-and-migrations.md)). They need a login that owns the
buildings and geometries tables and can create roles; the database owner, typically.

```sh
QUERY_ENGINE_MIGRATION_DATABASE_URL='postgres://<owner>:<password>@<host>:5432/<database>' npm run migrate -- up
```

To keep the owner's password out of your shell history, leave it out of the URL: the engine's database
client then reads it from the standard `PGPASSWORD` variable, which you can type without it being shown:

```sh
read -rsp 'Password: ' PGPASSWORD && export PGPASSWORD && echo
QUERY_ENGINE_MIGRATION_DATABASE_URL='postgres://<owner>@<host>:5432/<database>' npm run migrate -- up
unset PGPASSWORD
```

Expected output, on a database the engine has not seen before:

```
Applied 001.engine-schema-and-reader-role.
```

Run it again after every engine upgrade; when there is nothing new it prints
`Nothing to apply: the database is up to date.` To see where a database stands:
`npm run migrate -- status`.

Each migration runs in one transaction: if it fails, nothing from it is applied and the command prints the
database's reason. Two migrate commands cannot run at once against one database; the second waits.

The role belongs to the whole PostgreSQL server, so a second database on the same server (a frozen copy)
reuses it: run the migrations there too, and that database adds its own grants.

## Create the engine's login

Once per server, as a superuser or as the login whose migration created `query_engine_reader` (on
PostgreSQL 16 and later, the creator of a role holds the right to grant it). Choose your own login name; this guide
uses `query_engine_login`.

```sql
CREATE ROLE query_engine_login LOGIN;
\password query_engine_login
GRANT query_engine_reader TO query_engine_login;
-- A backstop: the engine already makes every transaction read-only itself.
ALTER ROLE query_engine_login SET default_transaction_read_only = on;
```

(`\password` is a psql command; it asks for the password so it never appears in your shell history.)

`\password` stores the password the way the server's `password_encryption` setting says. On a server
upgraded from an old version that setting can still be `md5`, and a `scram-sha-256` line in `pg_hba.conf`
(below) then refuses the login. Check with `SHOW password_encryption;`; if it says `md5`, run
`SET password_encryption = 'scram-sha-256';` in the same psql session before `\password`. A password stored
that way also works with `md5` lines.

Allow the login to connect from where the engine runs, in `pg_hba.conf`, for example for an engine on the
same machine:

```
host  <database>  query_engine_login  127.0.0.1/32  scram-sha-256
```

PostgreSQL uses the first line that matches, so if an earlier line already allows password logins from
there (many installations start with `host all all 127.0.0.1/32 scram-sha-256`), you need no new line.
Reload PostgreSQL after changing `pg_hba.conf`. Grant the engine's login nothing else: the service refuses
to start if its login can read or change more than the role allows (below).

## The field catalogue

The engine queries only the building attributes your platform defines and shows in its categories
([ADR-0002](decisions/0002-fields-come-from-the-host-field-definitions.md)). It learns them from a catalogue
file you generate from your own field definitions, `app/src/frontend/config/data-fields-config.ts`, and your
database's column types ([ADR-0009](decisions/0009-field-catalogue-file-format-and-commands.md)).

Generate it, from the engine's directory, against a database with your current schema (any login can read the
column types; the engine's own is fine). Your CI checks the catalogue against a database built from your
migrations ([below](#check-your-platform-in-ci)), so the surest source is a throwaway database built the same
way. A long-lived database (a developer's copy, or production) can differ from the migrations: if `check`
against it reports a column the catalogue names but the database lacks, that database has drifted from your
migrations, and the catalogue is not at fault.

```sh
QUERY_ENGINE_DATABASE_URL='postgres://query_engine_login:<password>@<host>:5432/<database>' \
  node src/cli.ts catalogue --definitions <your platform>/app/src/frontend/config/data-fields-config.ts \
  --output <your platform>/query-engine/catalogue.json
```

It prints a summary, for example:

```
Wrote .../catalogue.json: 278 fields in 12 categories; 28 columns excluded, each with its reason.
14 definitions have no buildings column and are not in the catalogue: uprns, planning_data, ...
```

(The numbers are colouring-core's at the commit the engine tests against.)

- The command reads the definitions without running them. From each `dataFields` entry it takes `category`,
  `title` and `items` (the allowed values); the categories' order and names come from `categoriesOrder` and
  `categoriesConfig` in the module the `Category` enum is imported from. It understands literals, `+` and
  template strings, arrays, objects, constants, enums and `require()` of a `.json` file, and stops with the file
  and line at anything else.
- Each `public.buildings` column becomes a field (text, integer, number or boolean, single or multi-valued)
  or goes on `excludedColumns` with its reason: no definition, a type plan format 1 cannot compare (dates,
  JSON), nested values, or allowed values that do not fit the column.
- A column with a database default is marked ambiguous: buildings nobody described hold the default, so a
  recorded default may not be an observation. Empty text and empty lists already count as blank.
- The output is the same for the same definitions and schema. Commit it in your platform's repository, and
  regenerate it whenever your field definitions or your buildings table change; your CI's `check` fails until
  you do (below).

Point the service at it with `QUERY_ENGINE_CATALOGUE_FILE`. In the container, mount it read-only and set the
path: [`compose.example.yaml`](../compose.example.yaml) mounts the file named by `CATALOGUE_PATH` in its
`.env` (a Compose variable, not an engine setting).

## Start the service

From source:

```sh
QUERY_ENGINE_DATABASE_URL='postgres://query_engine_login:<password>@127.0.0.1:5432/<database>' \
QUERY_ENGINE_CATALOGUE_FILE=/path/to/catalogue.json npm start
```

It logs JSON lines on standard output. When it is ready:

```
{"level":30,...,"msg":"Server listening at http://127.0.0.1:3100"}
```

Check it:

```sh
curl http://127.0.0.1:3100/health
# {"status":"ok"}
```

With the container, use [`compose.example.yaml`](../compose.example.yaml): copy it, put
`QUERY_ENGINE_DATABASE_URL` and the catalogue file's path (`CATALOGUE_PATH`) in a `.env` file beside it, and
follow the commands at its top. The container
answers its own health check on `/health`; `docker ps` shows it as `healthy`.

Stop the service with SIGTERM (Ctrl-C from a terminal); it finishes open requests and closes its database
connections.

## The start-up check

Before it serves anything, the service checks the database it points at. If anything is wrong it prints
every problem to standard error, starting `The query engine cannot start:`, and exits with code 1.

| Message starts | Cause | Fix |
|---|---|---|
| `QUERY_ENGINE_DATABASE_URL is not set` (or `QUERY_ENGINE_CATALOGUE_FILE`) | A required setting is missing | Set it ([Settings](#settings)) |
| `... must be a whole number of milliseconds` | A malformed timeout | Use a number such as `10000`, no unit |
| `could not reach the database server` | Wrong host or port, database down, or firewall. `(no answer)` means nothing replied within the engine's 5 s connect limit | Check the URL and that PostgreSQL listens where the engine can reach it |
| `the database refused the login` | Wrong user name or password, or `pg_hba.conf` | Check the login and `pg_hba.conf` |
| `the database named in the URL does not exist` | A typo in the database name | Check the URL's path |
| `The database has no table public.geometries` (or `buildings`) | Not a colouring-core database, or the wrong database | Point the URL at the host's database |
| `Table public.geometries has no column geometry_geom` | A layout that differs from colouring-core's | The engine needs colouring-core's `buildings` and `geometries` layout |
| `... has SRID 4326; the engine needs 3857` | Footprints stored in another projection | colouring-core stores footprints in EPSG:3857 |
| `QUERY_ENGINE_CATALOGUE_FILE names a file the engine cannot read` | Wrong path, or the file is not readable by the service's user | Check the path; in the container, the mount |
| `The catalogue file ... is not valid JSON` or `does not follow catalogue format 1.0.0` | The file was edited by hand or cut short | [Regenerate it](#the-field-catalogue) |
| `The catalogue lists the field ..., but public.buildings has no such column` | The catalogue was made from another schema, or a column was dropped | Regenerate it against this database's schema |
| `The catalogue says the field ... holds ..., but the column is ...` | A column's type changed | Regenerate it |
| `The engine's migrations have not been run` | New database | [Run the migrations](#run-the-engines-migrations) |
| `This database is missing engine migration(s) ...` | The engine was upgraded | Run the migrations |
| `... that this engine version does not ship` | An older engine against a newer database | Run the engine version that migrated it |
| `The engine's login cannot read public.buildings` (or `query_engine.migrations`) | Login not granted the role | `GRANT query_engine_reader TO <login>;` |
| `The engine's login is a superuser` | The service was given an administrator's login | Give it its own login ([above](#create-the-engines-login)) |
| `The engine's login has the CREATEDB attribute` (or `CREATEROLE`, `REPLICATION`, `BYPASSRLS`) | The login can administer the server or bypass table privileges | `ALTER ROLE <login> NOCREATEDB;` (and so on), or use the engine's own login |
| `The engine's login can read public.users` (or any other table, even one column of it) | The login has more than the role | Revoke the extra grant, or use the engine's own login |
| `The engine's login can change public.buildings` | The login can write, even to one column | Revoke the write grant, or use the engine's own login |
| `The engine's login can use sequence ...` | A grant on a sequence | Revoke it |
| `The engine's login can create objects in schema public` | A `CREATE` grant on a schema, often to `PUBLIC` on old databases | `REVOKE CREATE ON SCHEMA public FROM PUBLIC;` (PostgreSQL 15 and later do this by default) |
| `the start-up check could not finish` | An unexpected database error, named by its code | Look the code up in PostgreSQL's error codes appendix |

The database's own error messages are not printed, because they can name the login.

## Statement timeout

Every engine query runs inside a read-only transaction with `statement_timeout` set in that transaction, so
the timeout holds whatever the login's or database's own defaults are. Each engine connection also opens
with read-only transactions and the same timeout as its session defaults. A statement that runs longer is
cancelled by PostgreSQL and the request fails; nothing is left running.

The default is **10000 ms (10 s)**, five times the engine's 2 s answer target, so a slow but legitimate
question still answers while a runaway one cannot load the database the platform's contributors use. Raise
it with `QUERY_ENGINE_STATEMENT_TIMEOUT_MS` on a large database or slow server; lower it on a busy one.

## Reverse proxy

The host's own UI reaches the engine through one route on the host's web server, `/api/query/*`, forwarded
to the engine with the `/api/query` prefix removed. With nginx:

```nginx
location /api/query/ {
    proxy_pass http://127.0.0.1:3100/;
    # Send on only what the engine reads. nginx otherwise passes every request header,
    # including the platform's cookies, the referring page and the browser's name.
    proxy_pass_request_headers off;
    proxy_set_header Accept $http_accept;
    proxy_set_header Content-Type $content_type;
}
```

With this block the engine receives only `Accept`, `Content-Type`, `Content-Length` (nginx sets it for a
body) and `Host`, and the body unchanged (checked with nginx 1.30.8). nginx's time limit for an answer,
`proxy_read_timeout`, is 60 s by default, above the engine's [statement timeout](#statement-timeout); if you
raise the statement timeout towards 60 s, raise `proxy_read_timeout` too.

Keep the engine itself reachable only from the host (the default `127.0.0.1`, or the compose example's
`127.0.0.1:3100` port binding). The engine has no authentication of its own: it can serve only what its
restricted login can read, the building and footprint data, so put the host's own access rules on the proxy
route if that data is not public.

The proxy also decides whether people can use the queries at all: the query routes are `/v1/...`
([API reference](api-reference.md)), and a host that keeps the feature off (behind a feature flag, say)
leaves the route out, or forwards only `/api/query/health`.

### Forwarding from the host's own app instead

A host can forward the route from its own application server instead of nginx, for example to put it behind
the app's feature flag, or because its development set-up has no nginx. The forwarder should:

- remove the `/api/query` prefix and keep the rest of the path and the query string;
- pass the method and the body through unread and unchanged, before any body parser runs;
- pass on only `Content-Type`, `Accept` and `Content-Length` (or `Transfer-Encoding`), never cookies,
  `Authorization`, the referring page or the client's address;
- pass back the engine's status, body and headers, except those that belong to one connection
  (`Connection`, `Keep-Alive`, `Transfer-Encoding` and the like) and any `Set-Cookie`;
- answer in the engine's own error shape, `{"error": "<plain-English message>"}`, when the engine cannot be
  reached (502) or does not answer within a time limit above the statement timeout (504);
- cut the browser's answer off if the engine's is cut off part-way, and close the request to the engine if
  the browser gives up;
- log no body: a plan carries the area a person is looking at.

## Check your platform in CI

`node src/cli.ts check` tells you when your schema or your catalogue no longer matches the engine. It checks
the database's colouring-core buildings and footprint layout and the catalogue as the service does at start-up
(the file is valid; every field is a buildings column of its type), and adds the catalogue guard: every
`public.buildings` column must be a field or on the exclusion list, and every excluded column must still
exist. A new column, or a colouring-core upgrade that adds one, fails it until the catalogue is regenerated.
It reads `QUERY_ENGINE_DATABASE_URL` and `QUERY_ENGINE_CATALOGUE_FILE`, and exits 1 with each problem, or 0:

```
Check passed: the database has colouring-core's buildings and footprint layout, the catalogue's fields match their columns, and all 306 buildings columns are fields (278) or excluded (28) in the catalogue.
```

It does not need the engine's migrations or the engine's login: any login works, on a database built from
your own migrations alone. (The service's start-up check covers the migrations and the login.) In your
platform's CI, after building a throwaway PostGIS database from your migrations, from your repository's root
(with the catalogue committed at `query-engine/catalogue.json`):

```sh
git clone https://github.com/GeorgeAgyenim/ccrp-query-engine.git ccrp-query-engine
git -C ccrp-query-engine checkout <commit>   # the engine commit (later, release tag) your platform is pinned to
cd ccrp-query-engine && npm ci --omit=dev
QUERY_ENGINE_DATABASE_URL="$DATABASE_URL" QUERY_ENGINE_CATALOGUE_FILE=../query-engine/catalogue.json \
  node src/cli.ts check
```

`$DATABASE_URL` is the throwaway database's URL, from your CI's database service. Until releases begin
([Releases](#releases)), pin a commit of `main`, and move the pin when you upgrade the engine. To also catch
definitions that changed without a new catalogue, regenerate the catalogue into a temporary file and compare
it with the committed one.

The engine needs its own Node.js version (`.nvmrc`), which may differ from your platform's. Node.js 26
needs the system library `libatomic`, which the `postgis/postgis` images lack, so run these steps on the CI
runner itself, with the database as a service, not inside a database image used as the job's container.

An example GitHub Actions job, for a platform whose migrations are `migrations/*.up.sql`, applied in file-name
order as colouring-core's README applies them:

```yaml
jobs:
  query-engine-check:
    runs-on: ubuntu-24.04
    services:
      postgres:
        image: postgis/postgis:18-3.6   # your production database's major versions
        env:
          POSTGRES_HOST_AUTH_METHOD: trust   # a throwaway server only this job can reach
        ports: ["5432:5432"]
        options: --health-cmd "pg_isready -U postgres" --health-interval 5s --health-retries 20
    env:
      PGHOST: 127.0.0.1
      PGUSER: postgres
      QUERY_ENGINE_DATABASE_URL: postgres://postgres@127.0.0.1:5432/platform
    steps:
      - uses: actions/checkout@v7
      - uses: actions/checkout@v7
        with:
          repository: GeorgeAgyenim/ccrp-query-engine
          ref: <commit>
          path: ccrp-query-engine
      - uses: actions/setup-node@v7
        with:
          node-version-file: ccrp-query-engine/.nvmrc
      - name: Build a database from the platform's migrations
        run: |
          command -v psql || { sudo apt-get update && sudo apt-get install -y postgresql-client; }
          export LC_ALL=C   # the same file-name order on every machine
          psql -d postgres -c "CREATE DATABASE platform"
          psql -d platform -c "CREATE EXTENSION postgis; CREATE EXTENSION pgcrypto; CREATE EXTENSION pg_trgm;"
          for migration in migrations/*.up.sql; do psql -q -d platform -f "$migration"; done
      - working-directory: ccrp-query-engine
        run: |
          npm ci --omit=dev
          QUERY_ENGINE_CATALOGUE_FILE=../query-engine/catalogue.json node src/cli.ts check
          node src/cli.ts catalogue --definitions ../app/src/frontend/config/data-fields-config.ts \
            --output "$RUNNER_TEMP/catalogue.json"
          diff -u ../query-engine/catalogue.json "$RUNNER_TEMP/catalogue.json"
```

(colouring-core's migrations include a statement that fails harmlessly, a constraint added twice, so the
loop lets psql carry on past a failed statement, as the `psql < $migration` loop in core's README does.)

## Upgrading

1. Read the [changelog](../CHANGELOG.md) for the new version.
2. Stop the service.
3. Update the code (or image), then run the migrations.
4. Start the service; the start-up check confirms the database is current.

To revert the most recent engine migration: `npm run migrate -- down`. Reverting migration 001 removes the
`query_engine` schema and this database's grants to `query_engine_reader`, and drops the role itself when no
other database on the server still uses it. Dropping the role also removes it from the engine's login, so
after migrating up again, grant it again.

## Logs

JSON lines on standard output (pino's format, through Fastify). Each line has pino's level, time, process id
and the server's host name. A request adds one line with a per-process request counter (`reqId`), the
method, the route pattern (for example `/health`), the status and the duration. Never the query string,
body, headers or client address, which can carry a person's location or identity. Errors are logged by
name, database error code and stack frames, never by the database's message, which can repeat a value from
the query ([ADR-0008](decisions/0008-log-errors-without-personal-data.md)). At start the service logs the
address it listens on; it never logs the database URL.

## Releases

No image is published yet. When releases begin, each version tag `vX.Y.Z` will run a GitHub Actions
workflow that:
- builds the image from `Dockerfile` and pushes it to the GitHub Container Registry as
  `ghcr.io/georgeagyenim/ccrp-query-engine:X.Y.Z` (and `:X.Y`);
- attaches the JSON Schemas (`schemas/*.schema.json`) and the generated TypeScript types file
  (`schemas/query-engine.d.ts`, its header naming the versions) to the GitHub release;
- records the image digest in the release notes, so a host can pin the exact image.

A host then replaces `build: .` in its compose file with `image: ghcr.io/georgeagyenim/ccrp-query-engine:X.Y.Z`.
