# ADR-0006: The query engine is a separate, instance-neutral service in its own public repository

- Status: Accepted (one-way door: repository boundary and the engine's HTTP API)
- Date: 2026-11-26
- Ported from: Colouring Ghana ADR-0017 (2026-11-26; not public)
- Deciders: the first host's product owner (reuse goal, repository location and licence); Claude (Anthropic)
  as engineer (service shape, host contract)
- Related: ADR-0001 to ADR-0005, ADR-0007

## Context

The goal is a query engine and assistant that other Colouring Cities (CCRP) instances can reuse with little
code change apart from the user interface, and a user interface documented well enough that another instance
can rebuild it. Every instance is a fork of `colouring-cities/colouring-core`. Checked on 2026-11-26:
- colouring-core's field definitions and the first host's share one shape (`DataFieldDefinition`), so a
  field catalogue can be generated from any instance's own definitions (ADR-0002);
- colouring-core and the first host use the same map stack (Leaflet 1.7.1, react-leaflet 3, razzle 4,
  webpack 5), so one UI guide fits both;
- forks' backends diverge, and colouring-core's app runs on Node 18.

## Decision

- **Repository:** `GeorgeAgyenim/ccrp-query-engine`, public, GPL-3.0 (the same licence as colouring-core).
  Its documentation, decision records and integration guides live here, because other instances need them.
- **Shape:** one standalone, stateless, read-only HTTP service. It holds the plan schema, validator,
  field-catalogue loader, map-reference resolver, compiler, executor, answer assembler, assistant and
  download. It runs as its own process (from source or a container image) on its own Node version.
- **Host contract** (what an instance supplies, all as configuration):
  - a PostGIS database with colouring-core's building and footprint tables. The service checks the layout at
    start-up and refuses to start if it is missing.
  - a field catalogue file, generated by the engine's command from the instance's own
    `data-fields-config.ts` and database column types, plus a missing-value metadata file with evidence per
    field.
  - a footprint provenance record (source, licence, attribution).
  - a database login granted the engine's read-only group role (ADR-0007).
  - the language-model endpoint URL.
  - one reverse-proxy route, `/api/query/*`, to the service.
  - its own UI.
- **The engine owns its tables.** They live in the engine's own database schema, created by the engine's own
  migrations (ADR-0007). The engine never changes the instance's tables.
- **No client package.** The UI talks to the HTTP API only. Each release publishes the plan JSON Schema and a
  generated TypeScript types file, and the API offers a validate endpoint for the builder.
- **Each instance builds its own UI.** The first host builds the reference UI, and each UI ticket writes its
  chapter of the UI integration guide (`docs/ui-integration-guide.md`).

## Alternatives considered

| Alternative | What it would have meant | Why not |
|---|---|---|
| A library mounted in each instance's Express app | `app.use('/api/query', engine(...))` | Ties the engine to each fork's diverged backend, Node 18 and build setup |
| Contribute it straight into colouring-core | An upstream pull request | Upstream review would block the research demonstration; it can still be offered later |
| A git submodule inside each instance | Engine code vendored into forks | Hard for other teams to update; forks drift |
| An npm client package for UIs | A typed client and validator | Needs a package registry account and a second release line; the HTTP API plus a schema file is enough |

## Consequences

- Each instance runs one more process: its app and the engine.
- The engine's tests build their database from colouring-core's migrations at a pinned commit, which proves
  the host contract against core itself. Each instance runs the engine's `check` command in its own CI
  against its own migrations: the catalogue guard and the layout check.
- The engine's decision records stand alone. Each notes the record it came from in the first host's private
  documentation, and links nothing that is not public.
- Load and scale are as in ADR-0001. Each instance runs its own engine, so instances share no state.
- The repository is public. Fixtures are hand-made synthetic data. No instance's building data, credentials or
  personal data go in it, and the code names no instance.

## Plain-English summary

The question-answering engine is its own open-source program that any Colouring Cities platform can run next
to its website and point at its own database and field list. Each platform builds its own screens, following
a step-by-step guide written as the first platform's screens are built.
