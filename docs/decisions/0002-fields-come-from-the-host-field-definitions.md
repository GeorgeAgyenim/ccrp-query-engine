# ADR-0002: The engine's fields come from the host's field definitions, never from what the data holds

- Status: Accepted
- Date: 2026-11-26
- Ported from: Colouring Ghana ADR-0013, as amended by its ADR-0017 (both 2026-11-26; not public)
- Deciders: the first host's product owner, with Claude (Anthropic) as engineer
- Related: ADR-0003 (plan format), ADR-0006 (separate service)

## Context

Colouring Cities data are crowdsourced and sparse. In a typical instance most building columns are empty or
hold only their default, and contributions and bulk uploads fill more fields over time. An engine shaped
around today's filled fields, or around the values seen so far, would mishandle fields as they fill. The
research evaluation designs for the whole schema: it tests on a synthetically patched full-schema copy as
well as on the real sparse snapshot.

There are three candidate definitions of "the schema" in a colouring-core instance:
- the database columns, which still include fields inherited from upstream that the instance may not use
  (colouring-core began as Colouring London, so it carries UK planning fields such as BREEAM rating);
- the app's field definitions (`app/src/frontend/config/data-fields-config.ts` in a colouring-core fork:
  category, title and allowed values for each field);
- the data dictionary in the CCRP open manual.

## Decision

- The engine's fields are the ones the host defines and shows in its categories.
- One **field catalogue** file, generated by the engine's `catalogue` command from the host's own field
  definitions and database column types, gives each field's type and allowed values.
- An explicit **metadata file** per host adds what definitions lack, field by field, with its evidence:
  unit, numeric range, whether the field is multi-valued, which zero or false is a default or placeholder,
  and to which buildings it applies.
- The builder, validator, assistant grounding, completeness rules and the patched-copy generator all read
  the catalogue.
- Allowed values come from the definitions, never from values seen in the data.
- A database column with no definition is excluded and listed with its reason. The engine's `check` command
  fails if any building column is neither in the catalogue nor on the exclusion list.
- A recorded value outside a field's allowed list is reported as **non-conforming**, never merged into an
  allowed value or dropped.

## Alternatives considered

| Alternative | What it would have meant | Why not |
|---|---|---|
| Build around populated fields | Support only the fields and values present today | Breaks or misleads as soon as new contributions fill other fields |
| Every database column | Include inherited upstream fields | The engine, assistant and synthetic data would treat unused upstream fields as the host's fields |
| The CCRP manual's dictionary | Use the published document | A document, not the running system; it may differ from what a host deployed |

## Consequences

- Adding a field to a host's definitions makes it queryable with no engine code change.
- Adding a database column without a definition fails the host's `check` until it is defined or excluded.
- Metadata the definitions lack is added explicitly, with evidence, never guessed. Where evidence that a
  zero or false is a default is missing, the field is marked ambiguous and answers show both readings.
- Data defects, such as values cut off mid-label, show up as non-conforming until the host repairs them.

## Plain-English summary

The query engine learns which building details exist, and what values each may take, from the platform's
own definitions, not from the data entered so far. So a detail nobody has filled in yet still works the day
someone does. Leftover fields inherited from other platforms are left out and listed. Any value that does not
match the allowed list is flagged, not hidden.
