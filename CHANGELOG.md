# Changelog

Notable changes to the engine, newest first. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions follow
[Semantic Versioning](https://semver.org/spec/v2.0.0.html). Until 1.0.0 any release may change the API or the
settings; each change is listed here with what a host must do.

## [Unreleased]

### Added

- The query API, version 1 ([API reference](docs/api-reference.md); ADR-0011):
  `GET /v1/catalogue`, `GET /v1/plan-schema`, `POST /v1/validate` and `POST /v1/run`. A run counts the
  buildings in the current view that meet attribute conditions and answers with the spatial population, the
  recorded count, the confirmed matches, the share among recorded buildings (undefined, with its reason, when
  nothing is recorded), "as of", the plan, and one templated sentence.
  A question about a whole city is answered in a fraction of a second: on a made-up map of 20,000 buildings,
  under 0.1 s, where the first version took 3.9 s (ADR-0012). Hosts need do nothing.
- Plan format 1.0.0 (ADR-0010), published as `schemas/plan-1.schema.json`: a viewport area,
  filter steps in a CQL2-JSON subset (comparisons, `and`/`or`/`not`, `between`, `in`, the array functions,
  `recorded`, `blank`) and a number output. Invalid plans get plain-English messages naming the step and the
  field's title.
- Catalogue format 1.0.0 (ADR-0009), `schemas/catalogue-1.schema.json`, and
  `node src/cli.ts catalogue`, which writes a host's field catalogue from its `data-fields-config.ts` and
  column types without running the host's code.
- `node src/cli.ts check`, for a host's CI: the buildings layout and the catalogue match the database, and
  every buildings column is a field or excluded (the catalogue guard). Any login on a database built from the
  host's migrations will do.
- `schemas/query-engine.d.ts`, TypeScript types for the plan, catalogue and API bodies, generated by
  `npm run types`.
- The start-up check also refuses to start when the catalogue file is missing, invalid, or names a field
  whose column is missing or of another type.

- The service (`npm start`), on Node.js 26.13.1, configured by `QUERY_ENGINE_DATABASE_URL`,
  `QUERY_ENGINE_STATEMENT_TIMEOUT_MS` (default 10000), `QUERY_ENGINE_HOST` and `QUERY_ENGINE_PORT`.
- `GET /health`: 200 `{"status":"ok"}` when the database answers, 503 `{"status":"unavailable"}` when not.
- A start-up check that refuses to start, with a plain message, when colouring-core's buildings or footprint
  tables or columns are missing, footprints are not in EPSG:3857, the engine's migrations are not current, or
  the login is a superuser, holds CREATEDB, CREATEROLE, REPLICATION or BYPASSRLS, or can read, change,
  create or use more than the engine role allows (column grants included). Connecting gives up after 5 s.
- Engine migration 001: the `query_engine` schema and the no-login group role `query_engine_reader`, which can
  SELECT `public.buildings`, `public.geometries` and the engine's own tables only.
- `npm run migrate -- up | down | status`, run with `QUERY_ENGINE_MIGRATION_DATABASE_URL`.
- Every query runs in a read-only transaction with the statement timeout set inside it; each connection also
  opens read-only with the timeout as its session default.
- Request logs with the method, route pattern, status and duration only.
- A container image definition (`Dockerfile`) and a compose example beside an existing colouring-core
  database. No image is published yet.
- `npm test`: a throwaway PostGIS database built from colouring-core's migrations at a pinned commit, with
  synthetic fixtures; CI on PostgreSQL 18 with PostGIS 3.6.
- Documentation: host setup guide, API reference, UI integration guide (skeleton), decision records 0001 to
  0008, glossary, tools inventory, contributing guide.

### Host action

- Run the engine's migrations, create the engine's login and grant it `query_engine_reader`
  ([host setup guide](docs/host-setup.md)).
- Generate a field catalogue with the `catalogue` command, commit it with your platform, and set
  `QUERY_ENGINE_CATALOGUE_FILE` (now required). Run `check` in your CI
  ([host setup guide](docs/host-setup.md#the-field-catalogue)).
- If you put the earlier nginx block from the host setup guide in place, replace it with the new one, which
  stops passing the platform's cookies and the browser's other headers to the engine
  ([Reverse proxy](docs/host-setup.md#reverse-proxy)).

### Changed

- Contributor rules (safety, conventions, tests) now live in [CONTRIBUTING.md](CONTRIBUTING.md). Files
  used only by AI coding agents, such as `CLAUDE.md`, are no longer part of the repository.
- The README is now a short overview and setup guide for platforms. How to run the tests moved to the
  [testing guide](docs/testing.md).
- The host setup guide covers what the first platform to follow it found missing or unclear:
  - running the migrations without the owner's password on the command line;
  - servers that still store new passwords as `md5`, and when `pg_hba.conf` needs no new line;
  - generating the catalogue from a database built from the platform's migrations, and how a drifted
    database shows in `check`;
  - an nginx block that sends on only the headers the engine reads (the earlier one passed every header,
    cookies included);
  - forwarding `/api/query/*` from the platform's own app instead of nginx;
  - pinning an engine commit in CI, running the CI steps on the runner rather than inside a
    `postgis/postgis` container (Node.js 26 needs `libatomic`), and an example GitHub Actions job.
